Why Pydantic? — Data You Can Trust
Validate and clean messy data before it breaks your app

The problem: data from the outside world is dirty

Your program is happy as long as the data inside it is clean. But the moment data comes from outside — a user typing into a form, JSON from an API, a config file — you have no guarantees. The age field might arrive as the text "25" instead of a number. A required email might be missing entirely. One bad value and your app crashes deep inside, with a confusing error.

This matters a lot in GenAI apps: you constantly receive JSON from LLM tool calls, web APIs, and user prompts. You need a reliable gate that checks every piece of data before you use it.

🛂 Analogy — Passport control at an airport: Before anyone enters the country, an officer checks their passport: Is it real? Is it the right format? Are they who they claim to be? Only valid travelers get through. Pydantic is that officer for your data — it inspects every field, rejects anything wrong, and lets only clean, correct data into your program.

What Pydantic actually does

Pydantic is a Python library that does two jobs at once: it validates data (checks it follows your rules) and converts it into proper typed Python objects you can use safely.

Without PydanticWith Pydantic
You write manual if checks everywhereRules are declared once, in one place
"25" stays a string, surprises you later"25" becomes the integer 25
Missing fields crash randomlyYou get one clear error immediately
No autocomplete on raw dictsReal objects with editor autocomplete
💡 Why it matters: Pydantic powers FastAPI and many LLM frameworks. When you ask an LLM for "structured output", a Pydantic model is usually what describes the shape you want back. Learning it now pays off all week.

BaseModel & Field Types
Describe the shape of your data with simple type hints

Define a model by subclassing BaseModel

You create a model by making a class that inherits from BaseModel (remember inheritance from Day 2!). Each attribute gets a type hint — str, int, float, bool, list — and Pydantic enforces it for you.

📋 Analogy — A form template: A model is like a blank form that says "Name: ____ (text), Age: ____ (number)". Anyone filling it in must put the right kind of answer in each box. The template defines what valid looks like.
models.py
from pydantic import BaseModel

# A model is a class that inherits from BaseModel
class User(BaseModel):
    name: str
    age: int
    height: float
    is_active: bool = True      # default value

# Create an instance from raw data
u = User(name="Aisha", age="25", height=1.65)

print(u)
print(u.age, type(u.age))   # note: age came in as text "25"
▶ Output
name='Aisha' age=25 height=1.65 is_active=True 25 <class 'int'>
✨ Type coercion: We passed age="25" as text, but Pydantic automatically converted it to the integer 25. This is called coercion — it tidies up sensible inputs so you do not have to.

Optional fields, lists, and nested models

Use Optional[...] for a field that may be missing (it can be None), list[...] for collections, and you can even put one model inside another for nested data — exactly the shape real API JSON has.

nested.py
from pydantic import BaseModel
from typing import Optional

class Address(BaseModel):
    city: str
    country: str

class Profile(BaseModel):
    name: str
    nickname: Optional[str] = None   # may be missing
    hobbies: list[str] = []         # a list of strings
    address: Address                   # a nested model!

p = Profile(
    name="Omar",
    hobbies=["chess", "coding"],
    address={"city": "Cairo", "country": "Egypt"},
)

# Turn the whole object back into a plain dict
print(p.model_dump())
▶ Output
{'name': 'Omar', 'nickname': None, 'hobbies': ['chess', 'coding'], 'address': {'city': 'Cairo', 'country': 'Egypt'}}
ℹ️ model_dump(): In Pydantic v2, .model_dump() converts your object back into a normal Python dictionary — perfect for saving to a database or sending as JSON. Notice it even converted the nested address dict into a real Address object and back automatically.

Validation & Errors
What happens with bad data, and how to add your own rules

Bad data raises a ValidationError

If data does not fit the model and cannot be sensibly converted, Pydantic does not silently continue — it raises a ValidationError that tells you exactly which field was wrong and why.

🔍 Analogy — A quality inspector on a factory line: A faulty product never makes it to customers. The inspector pulls it off the line and writes a clear report: "Box 3, lid is cracked." Pydantic does the same — it stops bad data early and tells you precisely what failed.
validation_error.py
from pydantic import BaseModel, ValidationError

class User(BaseModel):
    name: str
    age: int

try:
    u = User(name="Sara", age="twenty")   # not a number!
except ValidationError as e:
    print(e)
▶ Output
1 validation error for User age Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='twenty']
⚠️ Catch it! A ValidationError is a normal Python exception. Wrap risky data in try / except (remember Day 2!) so a single bad input gives a friendly message instead of crashing your whole app.

Adding constraints with Field(...)

Type hints check the kind of value. Field(...) lets you add extra rules — minimum/maximum numbers, string lengths, and defaults — without writing any if statements.

ConstraintMeaningExample
gt / geGreater than / greater-or-equalField(gt=0)
lt / leLess than / less-or-equalField(lt=120)
min_lengthShortest allowed string/listField(min_length=3)
max_lengthLongest allowed string/listField(max_length=20)
defaultValue used when none is givenField(default=0)
constraints.py
from pydantic import BaseModel, Field

class Product(BaseModel):
    name: str = Field(min_length=3, max_length=40)
    price: float = Field(gt=0)          # must be positive
    stock: int = Field(default=0, ge=0)  # 0 or more

good = Product(name="Notebook", price=4.50)
print(good.model_dump())
▶ Output
{'name': 'Notebook', 'price': 4.5, 'stock': 0}

Custom rules with @field_validator

When a rule is too specific for Field (like "an email must contain an @"), write your own check with the @field_validator decorator — yes, another decorator from Day 2 in action!

custom_validator.py
from pydantic import BaseModel, field_validator

class Account(BaseModel):
    email: str

    @field_validator("email")
    @classmethod
    def must_have_at(cls, value):
        if "@" not in value:
            raise ValueError("email must contain @")
        return value

print(Account(email="hi@x.com"))   # ok
Account(email="oops")               # raises ValidationError
▶ Output
email='hi@x.com' pydantic_core._pydantic_core.ValidationError: 1 validation error for Account email Value error, email must contain @

async / await Basics
Do useful work while you wait instead of standing idle

Synchronous vs asynchronous

Normal ("synchronous") code does one thing at a time, top to bottom. If a line has to wait — for a website to reply, for a file to load, for an LLM to answer — your whole program just sits there frozen, doing nothing useful.

Asynchronous code is smarter: when something is waiting, it lets other work happen in the meantime, then comes back when the answer is ready.

🍳 Analogy — Cooking dinner: A beginner cook starts the rice, then stares at the pot for 15 minutes until it is done, and only then starts chopping vegetables. A smart cook starts the rice boiling, and while it cooks chops the veg and heats the pan. Same kitchen, far less wasted time. Async lets one program "cook several things at once".

The three keywords you need

async def Marks a function as a coroutine — a special function that is allowed to pause and resume.
await Pauses at a slow step and hands control back so other work can run. It waits without blocking everything else.
asyncio.run(main()) The starter button — it runs your top-level async function and manages all the pausing/resuming behind the scenes.
async_intro.py
import asyncio

async def make_tea():
    print("Boiling water...")
    await asyncio.sleep(2)        # pause, let others run
    print("Tea is ready! ☕")

async def main():
    await make_tea()

asyncio.run(main())          # the starter button
▶ Output (with a 2-second pause between lines)
Boiling water... Tea is ready! ☕
⚠️ Common beginner trap: You can only use await inside an async def function. And calling an async function without await does not run it — it just creates a coroutine object that sits there doing nothing.

Blocking vs async — see the difference

😴 Blocking (one at a time)

0s  start task A
    ⏳ wait... (idle)
3s  task A done
    start task B
    ⏳ wait... (idle)
6s  task B done

Total: 6 seconds

⚡ Async (overlap the waits)

0s  start A AND B
    ⏳ both waiting
       together...
3s  A done, B done

Total: ~3 seconds
💡 The key idea: Async does not make a single task faster. It stops you from wasting time waiting — many waits can overlap, so the total time shrinks dramatically.

Concurrency for API Calls
Fire many requests at once with asyncio.gather

Why this matters for LLM & web apps

GenAI apps spend most of their life waiting on the network — calling an LLM, fetching web pages, querying a database. If you do these one after another, the waits stack up. With async you can launch them all together and wait once.

🍽️ Analogy — A waiter taking orders: A slow waiter takes Table 1's order, walks to the kitchen, waits, comes back, then goes to Table 2. A good waiter collects orders from all tables first, then hands them to the kitchen together. Same kitchen, everyone is served much sooner.

asyncio.gather — run them all together

asyncio.gather(...) takes several coroutines, starts them all at once, and waits for every one to finish. The total time is roughly the time of the slowest single call — not the sum of all of them.

gather.py
import asyncio

async def ask_llm(prompt):
    print("Sending:", prompt)
    await asyncio.sleep(1)        # pretend the API takes 1s
    return f"Answer to {prompt}"

async def main():
    prompts = ["q1", "q2", "q3", "q4", "q5",
               "q6", "q7", "q8", "q9", "q10"]

    # Start all 10 calls at once, wait for all of them
    answers = await asyncio.gather(
        *[ask_llm(p) for p in prompts]
    )
    print(len(answers), "answers in ~1 second!")

asyncio.run(main())
▶ Output
Sending: q1 Sending: q2 ... (all sent immediately) Sending: q10 10 answers in ~1 second!

One-by-one vs all-at-once

🐌 Sequential

10 calls × 1 second each, done one after another.

Total: ~10 seconds

🚀 Concurrent (gather)

10 calls launched together, all waiting at the same time.

Total: ~1 second
💡 Real LLM use case: Imagine summarizing 50 documents. Sequentially that might take minutes; with gather you fire all 50 LLM calls at once and get them back in roughly the time of one. This is the single biggest speed-up in most GenAI pipelines. (In production you add a small limit so you do not flood the API with all 50 at literally the same instant.)

Tooling: Git, Structure, Testing, Streamlit
The everyday tools of a real GenAI engineer

Git — your project's time machine

Git saves snapshots of your code so you can go back, see history, and collaborate. Four commands cover almost everything you need at the start.

💾 Analogy — Save points in a video game: Git "commits" are save points. If you mess up, you reload an earlier save instead of restarting the whole game.
terminal
git init                 # start tracking this folder
git add .                # stage all changed files
git commit -m "first version"   # save a snapshot
git push                 # upload to GitHub

A sensible project structure

A clean folder layout makes any project easy to navigate — for you, your teammates, and future-you.

project tree
my_genai_app/
├── app.py            # Streamlit UI
├── src/              # your real code
│   ├── models.py     # Pydantic models
│   └── llm.py        # async API calls
├── tests/            # pytest tests
│   └── test_llm.py
├── requirements.txt  # dependencies
└── README.md
ℹ️ Tip: Add a .gitignore file so secrets and junk (like .env and __pycache__/) never get committed. Never push API keys to GitHub.

pytest — proof your code works

A test is a tiny function (name starts with test_) that uses assert to say "this should be true". Run pytest and it finds and runs them all, reporting pass or fail.

🚦 Analogy — A smoke alarm: Tests quietly watch your code. The moment something breaks, they go off — so you find bugs before your users do.
test_math.py
def add(a, b):
    return a + b

# pytest finds any function starting with test_
def test_add():
    assert add(2, 3) == 5      # must be true to pass
    assert add(-1, 1) == 0
▶ Output (run: pytest)
test_math.py . [100%] 1 passed in 0.01s

Streamlit — a web app from a Python script

Streamlit turns a plain Python file into an interactive web app — no HTML, CSS, or JavaScript needed. It is the fastest way to put a friendly face on your GenAI project.

app.py
import streamlit as st

st.title("My First AI App 🤖")
st.write("Ask me anything below:")

name = st.text_input("Your name")
if name:
    st.write(f"Hello, {name}! 👋")
terminal
streamlit run app.py    # opens the app in your browser
💡 Why it matters: By the end of the bootcamp you will wrap your LLM logic in a Streamlit app so anyone — not just programmers — can use what you built. st.title, st.write, and st.text_input already get you a working demo.
