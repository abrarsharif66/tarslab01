Document Loaders & Ingestion
Bringing your own data into LangChain

Why do we need loaders?

An LLM only knows what it learned during training. It has never seen your company handbook, your PDFs, or your website. To make the model useful on your data, we first need to load that data into LangChain — this is the very first step of RAG (Retrieval-Augmented Generation).

LangChain provides loaders for almost any source: text files, PDFs, web pages, CSVs, Notion, YouTube transcripts and more. Every loader turns your raw source into a list of standard Document objects.

🍳 Analogy: A loader is like carrying raw ingredients into the kitchen. The PDF, the website, the CSV — they are vegetables, spices and meat from outside. The loader brings them in and puts them on the counter in a tidy, standard format so the chef (the LLM) can actually cook with them.

The Document object — page_content + metadata

No matter the source, a loader returns Document objects. Each one has two parts: page_content (the actual text) and metadata (extra info like the source file, page number, or URL).

loaders.py
# 1) Load a plain text file
from langchain_community.document_loaders import TextLoader

loader = TextLoader("notes.txt")
docs = loader.load()       # -> list of Document objects

# 2) Load a PDF (one Document per page)
from langchain_community.document_loaders import PyPDFLoader
pdf_docs = PyPDFLoader("report.pdf").load()

# 3) Load a web page
from langchain_community.document_loaders import WebBaseLoader
web_docs = WebBaseLoader("https://example.com/blog").load()

# Peek inside the first Document
print(docs[0].page_content[:60])
print(docs[0].metadata)
▶ Output
Welcome to the GenAI Bootcamp. Day 9 covers LangChain {'source': 'notes.txt'}
ℹ️ Note: Loaders live in langchain_community.document_loaders. Some need an extra package (e.g. pypdf for PyPDFLoader). The pattern is always the same: create the loader, call .load(), get back Document objects.

A few common loaders

Text Splitters — Chunking Big Documents
Cutting documents to fit the LLM's context window

Why split at all?

Every LLM has a context limit — a maximum amount of text it can read at once. A 300-page PDF will never fit. So before we feed documents to a model (or store them for RAG), we cut them into smaller chunks.

📏 Analogy: Imagine reading a giant scroll through a small window. You can only see one section at a time. Splitting is like cutting that scroll into neat pages that each fit through the window — and chunk_overlap is like repeating the last sentence of each page at the top of the next one, so you never lose the thread mid-sentence.

chunk_size and chunk_overlap

chunk_size = how big each piece is (in characters or tokens). chunk_overlap = how much each chunk repeats from the previous one, so context isn't lost exactly at the cut point.

splitter.py
from langchain_text_splitters import RecursiveCharacterTextSplitter

text = "LangChain makes it easy to build LLM apps. " * 20

# The DEFAULT, smartest splitter
splitter = RecursiveCharacterTextSplitter(
    chunk_size=100,        # max ~100 chars per chunk
    chunk_overlap=20,      # repeat 20 chars between chunks
)

chunks = splitter.split_text(text)
print("Number of chunks:", len(chunks))
print("First chunk:", chunks[0])

# Or split Document objects directly
split_docs = splitter.split_documents(docs)
▶ Output
Number of chunks: 11 First chunk: LangChain makes it easy to build LLM apps. LangChain makes it easy to build LLM apps.

Which splitter should I use?

RecursiveCharacterTextSplitter is the default and best for most text. It tries to split on the largest natural boundary first — paragraphs → lines → sentences → words — so chunks stay readable.

RecursiveCharacterTextSplitter

Smart default. Respects paragraph and line boundaries. Use for plain text, articles, docs.

CharacterTextSplitter

Simple. Splits on a single separator (default "\n\n"). Less context-aware.

For structured content there are specialized splitters too: HTMLHeaderTextSplitter splits by HTML headings, and RecursiveJsonSplitter splits JSON while keeping the structure intact.

📌 Choosing chunk size: Smaller chunks (300–500 chars) = more precise retrieval but more pieces. Larger chunks (1000–2000) = more context per piece but less precise. A common starting point is chunk_size=1000, chunk_overlap=200 — tune from there.

Prompt Templates — Reusable, Parameterized Prompts
Separate the wording from the data

Why templates instead of plain strings?

You will rarely send the exact same prompt twice — only the data changes. A prompt template is a prompt with {variables} in it. You write the wording once, then fill in the blanks each time. This keeps your prompts clean, reusable and easy to edit.

✉️ Analogy: A prompt template is a fill-in-the-blank form letter. "Dear ___, thank you for ordering ___." The letter (the wording) is written once; you just slot in a new name and product for each customer. Same prompt structure, different data every time.

PromptTemplate vs ChatPromptTemplate

PromptTemplate builds a single string. ChatPromptTemplate builds a list of chat messages (system + human), which is what modern chat models actually expect.

prompts.py
from langchain_core.prompts import PromptTemplate, ChatPromptTemplate

# Simple string template
prompt = PromptTemplate.from_template(
    "Write a one-line tagline for a {product}."
)
print(prompt.format(product="coffee shop"))

# Chat template with system + human messages
chat_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a witty marketing assistant."),
    ("human",  "Write a tagline for a {product}."),
])

messages = chat_prompt.format_messages(product="coffee shop")
for m in messages:
    print(m.type, "->", m.content)
▶ Output
Write a one-line tagline for a coffee shop. system -> You are a witty marketing assistant. human -> Write a tagline for a coffee shop.
📌 Remember: The system message sets the role/behaviour ("you are a helpful tutor"); the human message carries the actual request and the {variables}. Keep your changing data in variables, never hard-coded in the template.

LCEL Chains — Piping Components with |
LangChain Expression Language: the modern way to build

The pipeline mental model

LCEL (LangChain Expression Language) lets you connect components with the pipe operator |, just like Unix pipes. Data flows left → right: the output of one piece becomes the input of the next.

the_pattern.py
chain = prompt | model | parser
🏭 Analogy: Think of an assembly line. The raw input enters at the left; the prompt station shapes it into a request, the model station turns it into a response, and the parser station polishes it into clean output. Each station passes its result to the next — that is exactly what | does.
promptTakes your variables (e.g. {product}) and produces a formatted prompt/messages.
modelSends those messages to the LLM and returns an AI message.
parserTurns the AI message into the final clean data (a string, a dict, etc.).

A runnable chain with .invoke()

You call the chain with .invoke(), passing a dict of the template variables. Any chat model works — use ChatOpenAI or ChatAnthropic (the rest of the chain is identical).

lcel_chain.py
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_anthropic import ChatAnthropic
# (or: from langchain_openai import ChatOpenAI)

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a witty marketing assistant."),
    ("human",  "Write a tagline for a {product}."),
])

model  = ChatAnthropic(model="claude-sonnet-4-5")
parser = StrOutputParser()

# Build the chain by piping the pieces together
chain = prompt | model | parser

# Run it!
result = chain.invoke({"product": "coffee shop"})
print(result)
▶ Output
Life's too short for bad coffee. ☕
ℹ️ Why LCEL? Because it pipes components, every chain automatically gets streaming, batching and async for free — and you can read the data flow at a glance, left to right.

Output Parsers — Turning Text into Clean Data
From free-form text to reliable objects

Why parse the output?

An LLM always returns text. But your program usually wants data — a clean string, a number, or a structured object you can use directly. Output parsers do that conversion at the end of the chain.

🥡 Analogy: The model hands you a messy takeaway bag with everything mixed together. A parser is the person who unpacks it and lays each item neatly on a plate — so your code gets a tidy dict or object instead of having to dig through raw text.
str_parser.py
from langchain_core.output_parsers import StrOutputParser

# The simplest parser: pulls the plain text out of the AI message
parser = StrOutputParser()
chain = prompt | model | parser

text = chain.invoke({"product": "bakery"})
print(type(text), "->", text)
▶ Output
<class 'str'> -> Freshly baked happiness, every morning.

Structured output with Pydantic

When you need reliable JSON/objects (not free text), define the shape with a Pydantic model and let the LLM fill it in. The modern, easiest way is model.with_structured_output(YourModel).

structured.py
from pydantic import BaseModel, Field

# Define the exact shape you want back
class Tagline(BaseModel):
    slogan: str = Field(description="the catchy line")
    tone: str = Field(description="e.g. fun, serious")

# Ask the model to return that structure
structured_model = model.with_structured_output(Tagline)
chain = prompt | structured_model

result = chain.invoke({"product": "coffee shop"})
print(result.slogan)
print(result.tone)
print(result.model_dump())   # as a dict
▶ Output
Life's too short for bad coffee. fun {'slogan': "Life's too short for bad coffee.", 'tone': 'fun'}
ℹ️ Back to Day 3: Remember Pydantic from our Python data-validation lesson? Same tool here. It defines and validates the exact fields and types you want — which is why the LLM's output comes back as a clean, type-checked object instead of guesswork. (The older PydanticOutputParser does the same job; with_structured_output is the newer, simpler way.)

Putting It Together — A Multi-Step Chain
Loader → Splitter → Prompt → Model → Parser

The full pipeline

Now we combine every block from today into one end-to-end flow: load a document, split it, summarize the first chunk with a prompt + model, and get clean text out with a parser.

LoadRead the file into Document objects with a loader.
SplitCut the documents into manageable chunks.
PromptInsert the chunk text into a prompt template.
ModelSend it to the LLM via the LCEL chain.
ParseUse StrOutputParser to get a clean summary string.
end_to_end.py
from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_anthropic import ChatAnthropic

# 1) LOAD
docs = TextLoader("article.txt").load()

# 2) SPLIT
splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.split_documents(docs)

# 3) PROMPT + 4) MODEL + 5) PARSER  (one LCEL chain)
prompt = ChatPromptTemplate.from_messages([
    ("system", "You summarize text in one clear sentence."),
    ("human",  "Summarize this:\n\n{content}"),
])
model  = ChatAnthropic(model="claude-sonnet-4-5")
chain  = prompt | model | StrOutputParser()

# Run on the first chunk
summary = chain.invoke({"content": chunks[0].page_content})
print(summary)
▶ Output
LangChain provides loaders, splitters, prompts, chains and parsers that let developers feed their own data to an LLM and get clean, structured results.
🚀 This is the basis of RAG! Load → split → (embed & store) → retrieve → prompt → model. You just built everything except the embed/store/retrieve step. Add a vector store and you have full Retrieval-Augmented Generation — that's Day 12. You're ready.
